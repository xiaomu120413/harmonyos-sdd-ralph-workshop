## 2. 开发循环运行账（课堂模板）

> 本表表达正确的开发顺序和证据门。当前运行日志未完整入库，结果列保留 `PENDING`，不冒充真实 PASS 账。

| 轮次 | 当前任务 | 唯一未知 | 必须保存的证据 | 结果 | 进入下一轮的门 |
|---|---|---|---|---|---|
| R1 | T01 产物/注入 | OHOS bridge 是否真正进入目标 HAP 并 attach | arm64 symbol、library hash、attach log | `PENDING` | 产物身份与 attach 同时成立 |
| R2 | T01 硬解选择 | 目标设备是否提供并选中 hardware H.264 decoder | capability、decoder name、configure/prepare/start | `PENDING` | 硬件 decoder identity 可见；不支持则结束 |
| R3 | T02 一帧输出 | 压缩输入是否产生合法 native output | frameId、input/output PTS、size、format、stride/planes | `PENDING` | input/output 可关联且格式可导入 |

## 3. 为什么早期方案会“局部合理、整体错误”

| 早期判断 | 为什么看起来合理 | 反证 |
|---|---|---|
| 创建硬件 decoder 成功就算接入完成 | API 已返回成功 | 没有输出或仍走旧 GDI |
| 截图正常说明 renderer 正确 | 采样瞬间可见 | 下一帧黑屏、闪烁或旧帧覆盖 |
| 两个 decoder 可并行处理 AVC444 | luma/chroma 是两路流 | FreeRDP 原生语义共享一个 H264 状态机 |
| command 完成立刻 present | 可以尽快显示 | 与 EndFrame 边界不一致 |
| GPU 开启就 suppress GDI | 避免重复工作 | GPU 尚未完整消费 command 时失去 fallback |

## 4. 最早异常表

```text
command received
→ subsystem selected
→ input queued
→ decoded output valid
→ format/stride/planes valid
→ retained/dirty state applied
→ owner correct
→ EndFrame present
→ next frame continues
```

每轮只修第一处 FAIL。没有证据时补一条能区分两个分支的日志，不做高频全链路刷屏。

## 5. 三类问题的第一观测

| 现象 | 第一条证据链 | 本轮最小修改边界 |
|---|---|---|
| decoder 有 output 但黑屏 | native buffer import → composite → pendingFrameId → matched EndFrame → target generation | 第一个 FAIL 所属的 import/composite/present/lifecycle 边界 |
| 粉/绿块或局部错位 | output format/stride/planes → dirty rect → retained background | format/plane math 或 retained state，不先改色彩矩阵 |
| 越播越卡 | queue depth/age → decodeUs/compositeUs/present gap → target state | 首个持续恶化指标的 owner，不直接加线程 |

## 6. 真实 Session 边界教训

用户只授权移除一个 cache 尝试时，AI 扩大为删除整条实现路径。即使 build 通过，也因超出授权范围判 `Trace FAIL`。正确处理是停手、识别精确对象、只回滚越界部分，并回到最近可信 checkpoint。

## 7. 复盘产物

- last-good / first-abnormal frame。
- 被推翻的假设及直接证据。
- 最小修正 diff。
- 重跑目标、回归、故障注入、A/B 的 Reviewer verdict。
