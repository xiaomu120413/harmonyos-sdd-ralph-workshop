# AI 文档生成与审阅链｜这些文档从哪里来，为什么必须存在

这组文档不是 AI 自己“写了一套漂亮材料”，也不是开发结束后的补作业。它们是复杂需求中的阶段性控制面：把当前事实、推理、人的决定、证据状态和下一阶段入口固定下来，让后续 Session 不必重新猜上下文。

## 1. 为什么不能直接从需求跳到代码

GPU 案例同时跨越 30 万行级以上开源库、多个已有平台后端、HarmonyOS 平台 API、协议帧语义、NativeBuffer/Surface 所有权和真实性能验收。若只靠聊天上下文，AI 很容易：

1. 把文件名、类型名或旧平台实现误当成当前运行事实；
2. 调研了一堆资料，却没有形成可选择的方案；
3. 方案在开发过程中漂移，失败时不知道应回到哪个决策；
4. 一次修改 decoder、renderer、queue 与 AVC444，失去可证伪边界；
5. 用 build success、API success 或单张截图替代端到端验收。

所以每个阶段都必须形成一份“可被下一阶段消费”的文档，而不是只留聊天记录。

## 2. 文档不是 AI 单独生成，而是四步闭环

```text
输入包（问题 + 仓库锚点 + 证据状态）
  → AI 只读分析（检索、比较、列未知、提出候选）
  → Human Review（核对源码/来源、冻结取舍、拒绝越权结论）
  → 受控文档（FACT / INFERENCE / PENDING + 下一阶段入口）
```

四个角色不能混在一起：

| 环节 | 谁负责 | 必须留下什么 |
|---|---|---|
| 输入 | Human / Planner | 本轮问题、允许读取的范围、已有事实、禁止假设 |
| 分析 | AI / Explorer | 源码锚点、来源、候选解释、未知与下一条验证命令 |
| 决策 | Human / Reviewer | 哪些结论接受、拒绝或保留 `PENDING`，为什么 |
| 交接 | 文档 | 下一阶段可以直接消费的约束、证据门和 Stop 条件 |

## 3. 八份文档怎样一份一份生成

| 阶段文档 | 输入 | AI 的动作 | Human Review | 为什么要做 | 下一阶段怎么用 |
|---|---|---|---|---|---|
| `01-问题与基线.md` | 用户现象、本地 Session、可用媒体 | 把 CASE FACT、REPO FACT、PENDING 分开 | 冻结“当前走 CPU/软件路径”，不编造 CPU/FPS | 防止一上来就选方案 | 给 codebase map 一个明确问题 |
| `02-大代码库认知地图.md` | 问题、仓库文件清单、入口符号 | 用 `rg` 和调用关系回答五个导航问题 | 抽查 `path::symbol` 能否跳转，删除“像事实的猜测” | 控制上下文预算 | 告诉调研应比较哪些接口和边界 |
| `03-跨平台实现调研.md` | codebase map、FFmpeg/OpenH264/MF/MediaCodec/OH_AVCodec 实现 | 比较共同生命周期、失败语义与平台差异 | 核对源码/官方来源，把推断标成推断 | 避免照抄其他平台 API | 给 ADR 提供候选方案与取舍依据 |
| `04-ADR-GPU-001-*.md` | 调研表、当前仓库约束、风险清单 | 生成方案候选、Alternatives、Deferred、Evidence Gate | Human 选择接管/合成/回退边界 | 开发前冻结方向 | 只允许 spike 验证 ADR 的最大未知 |
| `05-最小能力穿刺计划.md` | ADR 的 Evidence Gate 与最大未知 | 倒推出 SP-01～SP-05 和每步证据 | 确认每步只证明一个接口边界 | 低成本证伪方案 | 穿刺结果决定哪些任务现在可拆 |
| `tasks/T-GPU-*.md` | 穿刺结果、源码边界、验收目标 | 按一个可观察结果切片，补 Allowed/Forbidden/Verify/Stop | 检查任务是否越界、验收是否先于实现 | 防止 AI 大片改动 | Ralph 每轮只领取一张卡 |
| `07-开发排障复盘.md` | commit、runId、build/device/frame trace | 找第一处 `expected != actual`，列假设和下一条命令 | 决定修复边界或 `REPLAN/ESCALATE` | 让失败产生新知识 | 回写 Task、ADR 或下一轮 progress |
| `06-工程验收计划.md` | 所有 Task AC、运行证据、用户场景 | 汇总 Trace/Outcome/Regression/Soak 矩阵 | 用系统事实和用户结果做最终裁决 | 防止局部 GREEN 冒充交付 | 形成 reviewer verdict 与发布门 |

## 4. 课堂上怎么演示“生成”，而不是只展示成品

以 `03-跨平台实现调研.md` 为例，现场只演五个动作：

```text
1. Human 给输入：当前调用链 + 需要回答的四个问题
2. AI 只读检索：现有后端的 Init / Decompress / Uninit 与 buffer 状态
3. AI 起草：共同契约、平台差异、来源、仍未知
4. Human Review：事实能否回到源码/官方 API；推断是否明确标注
5. 文档交接：只有通过审阅的结论进入 ADR，未证实项留 PENDING
```

为什么必须这样做：调研的目标不是“知道更多”，而是减少 Architecture Decision 中的未知。如果某段调研不能改变候选方案、风险或证据门，就不应进入主文档。

## 5. 一张可截图的 Document Evidence Card

```markdown
Document: 03-跨平台实现调研.md
Question: 其他平台的 H.264 后端，哪些契约可复用？
Input: codebase-map + 4 个平台实现 + OH_AVCodec 能力
AI action: 对齐生命周期、buffer 状态、失败传播和释放语义
Human decision: 复用契约，不复制 API/线程模型/Surface ownership
Evidence: path::symbol / official API / FACT-INFERENCE-PENDING
Output: 三个候选方案 + 推荐边界 + ADR 输入
Why: 防止“Android 能跑，所以 HarmonyOS 直接照抄”的错误迁移
```

每份课堂文档都应能用这张卡解释。如果讲师回答不了 `Input / Human decision / Why / Next`，这份文档就仍像 AI 生成的“黑盒答案”。

## 6. 现场 Prompt：先生成证据结构，再生成正文

```text
你正在生成阶段文档，不是在给最终方案。

输入：<当前问题、允许读取范围、已有 FACT、PENDING>
请先输出：
1. 本文档要减少的唯一未知；
2. 需要读取的源码/官方资料和理由；
3. FACT / INFERENCE / PENDING；
4. 需要 Human 决定的选项；
5. 下一阶段将消费哪些字段；
6. 如果证据不足，明确 Stop，不生成强结论。

Human Review 后，再把确认内容写入正式 Markdown。
```

## 7. Reviewer 的六个问题

1. 这份文档的输入能否回到具体文件、日志、运行或用户决定？
2. AI 的事实和推断是否被明确分开？
3. Human 到底确认了什么，而不是笼统“看起来没问题”？
4. 文档是否减少了下一阶段的未知？
5. 下一阶段能否直接消费它的字段，而不用重读整段 Session？
6. 哪些结论仍应是 `PENDING / UNKNOWN`？

只有六问都能回答，这份文档才是工程资产，而不是聊天纪要。
