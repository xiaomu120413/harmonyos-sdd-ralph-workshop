# 阶段 3｜跨平台 H.264 实现调研

## 1. 调研问题

FreeRDP 已经如何支持不同平台的 H.264 解码？这些实现能帮助 HarmonyOS 复用哪些 decoder 生命周期，又有哪些 RDPGFX/GPU 显示语义不能由 decoder subsystem 单独解决？

## 2. 代码事实对照

| 实现 | 代码入口 | 复用价值 | 不可照抄部分 |
|---|---|---|---|
| FFmpeg | `h264_ffmpeg.c` | 软件 fallback、I420/YUV 语义 | 软件线程与性能模型 |
| OpenH264 | `h264_openh264.c` | 正确性基线、解码状态 | 输出格式和平台资源模型 |
| Windows Media Foundation | `h264_mf.c` | 硬解创建、输入、输出、释放 | COM 与 Windows surface |
| Android MediaCodec | `h264_mediacodec.c` | 移动平台 buffer 生命周期、format change | Android buffer ID 和 API 时序 |
| HarmonyOS AVCodec | `h264_ohos_decoder.c`、`h264_ohos_decoder_buffer.c` | capability、AVBuffer、硬件 decoder、stride/plane | 只解决原生 H.264 subsystem 解码；GPU takeover 仍需 command、dirty rect、owner、EndFrame |

这里必须区分两条路径：

```text
原生回退：gdi_SurfaceCommand → H264_CONTEXT_SUBSYSTEM → GDI
GPU 接管：OHOS RDPGFX bridge → App compositor → OH_AVCodec → retained composite → EndFrame
```

跨平台 decoder 实现能够回答 Create/Configure/Input/Output/Flush，但不能直接回答“当前 RDPGFX command 是否可以被消费”“什么时候 suppress GDI”“哪个 owner 可以 present”。

## 3. 可迁移契约

```text
Create → Configure → Register/Prepare → Start
Input compressed sample
Wait for / receive bounded output
Validate size / format / stride / planes
Publish decoded state
Flush / Stop / Destroy
Failure → explicit fallback or UNKNOWN
```

## 4. 调研证据等级

- 当前仓库源文件：主证据。
- HarmonyOS 官方 API/SDK：平台能力证据。
- 博客、问答、示例：只作为搜索线索。
- AI 对其他平台的概括：必须回到代码或官方文档核对。

## 5. 调研输出

结论不是“Android 有 MediaCodec，所以 HarmonyOS 也能照抄”，也不是“实现一个 `H264_CONTEXT_SUBSYSTEM` 就完成 GPU 优化”。最终方案复用其他平台的 decoder 生命周期经验，但接入点选择 OHOS RDPGFX bridge；App compositor 直接管理 `OH_AVCodec`、native buffer、retained state、owner 与 EndFrame。原生 `H264_CONTEXT_SUBSYSTEM / GDI` 保留为 fallback。
