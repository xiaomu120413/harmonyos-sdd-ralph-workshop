## 2. 五个导航问题

1. H.264 命令从哪里进入？
2. 当前 command 是进入 GPU compositor，还是回到 GDI/H.264 subsystem？
3. 解码输出的格式、stride 和 plane 是什么？
4. 哪个组件拥有显示 Surface，何时 present？
5. 如何证明没有走软件/GDI fallback？

## 3. 逐层索引

| 层 | 关键入口 | 本轮结论 |
|---|---|---|
| 原生 GDI 路径 | `libfreerdp/gdi/gfx.c`、`codec/h264.c` | `gdi_SurfaceCommand` 分发 AVC420/444；`H264_CONTEXT_SUBSYSTEM` 属于原生 decoder/fallback 契约 |
| 平台 decoder 对照 | `h264_ffmpeg.c`、`h264_openh264.c`、`h264_mf.c`、`h264_mediacodec.c`、`h264_ohos_*` | 可借鉴 decoder 生命周期，但不能覆盖 dirty rect、owner 与 EndFrame 问题 |
| OHOS RDPGFX bridge | `client/OHOS/ohos_rdpgfx_*` | 保存原回调，校验 command，决定 GPU consumed 或交还 GDI |
| App GPU 路径 | `rdpgfx_pipeline.*`、`avc420_gpu_compositor*`、`render_output_owner.*` | 直接管理 OH_AVCodec、native buffer、retained composite、owner 与 EndFrame present |

## 4. 大库阅读法

```text
需求问题
  → 搜 3 个入口：协议入口 / OHOS 注入点 / App 输出点
  → 只追 1 条 SurfaceCommand 调用链
  → 在 5 个判定门停下：candidate / decoder / output / owner / EndFrame
  → 写 codebase-map.md，不写全仓总结
  → 把未知转成下一轮最多 5 个文件
```

| 导航问题 | 第一个搜索词 | 要产出的结论 | 不允许的推断 |
|---|---|---|---|
| H.264 command 从哪进 | `gdi_SurfaceCommand` / `SurfaceCommand =` | wrapper 与 original callback 调用关系 | 看到文件名就声称运行时必经过 |
| GPU 还是 GDI | `consumed` / `candidate` / `hooks.surfaceCommand` | takeover 前后的分支和回退 | 把一个开关当完整状态机 |
| decoder 输出是什么 | `OH_AVBuffer_GetNativeBuffer` | frame/PTS/format/stride/planes | 有 callback 就当输出合法 |
| 谁显示、何时显示 | `pendingFrameId` / `PresentEndFrame` / `eglSwapBuffers` | owner 和 matched EndFrame 边界 | decode 后直接 swap |
| 怎么证明路径 | `frameId` / `decoder` / `owner` / `present` | 一条可关联 frame trace | 用截图或 build PASS 替代 runtime path |

### `codebase-map.md` 一条记录的固定格式

```markdown
Symbol: <path>::<function>
Input: <command/buffer/state>
Output: <return/state/next callback>
Owner: <who owns the state>
Fallback: <where it goes on failure>
Evidence: REPO FACT | RUN FACT | UNKNOWN
Next read: <maximum five files>
```

## 6. Reviewer 判定

- 代码锚点可定位：`PASS`。
- 当前运行实际经过哪条 decoder：仍需 runtime evidence。
- “读完整仓库后再设计”：拒绝，原因是上下文成本高且无关信息会污染判断。
