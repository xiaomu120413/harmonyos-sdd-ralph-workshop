# 阶段 6｜GPU 路径工程验收计划

## 1. 验收原则

验收只判定，不修改生产代码。实现完成后冻结 accepted code commit，Reviewer 使用同一设备、场景和证据口径独立运行。发现缺陷时输出 FAIL 和新 Story，不在验收过程中顺手修复。

四层证据必须分开：

| 层 | 核心问题 | 主证据 |
|---|---|---|
| Trace | 真实运行是否进入目标 path | decoder/path/frame/owner/present 原始日志 |
| Behavior | 帧语义、画面和回退是否正确 | ordered trace、fault injection、视频、状态转移 |
| Outcome | 同场景卡顿和资源指标是否达到冻结目标 | before/after CSV 与同场景视频 |
| Scope | 实现和验收是否遵守 Story 边界 | docs checkpoint、diff、测试、Reviewer verdict |

任一层缺证据时只能为 `PENDING/UNKNOWN`，不能由另一层代替。

## 2. 验收前置条件

- S0～S6 均有独立 verdict 和原始证据路径。
- `00-证据状态总表.md` 已更新到 accepted code commit。
- before/after 的设备、网络、分辨率、片段、时长和采样口径已冻结。
- 性能、队列和 soak 阈值已由项目负责人写入验收包；未冻结时相应项保持 `TARGET TBD`。
- fault injection 有清理步骤，执行后可恢复正常路径。
- Reviewer 不使用 Implementer 的摘要替代原始日志。

不满足任一条件时整体结果为 `NOT READY`。

## 4. 执行顺序

1. 记录 accepted commit、工作区状态、HAP hash、设备和场景 identity。
2. 按 `13` 第 5.2 节执行 FreeRDP 构建、runtime 同步、2in1 构建、安装和启动。
3. 依次执行 PATH → AVC420 → fallback → AVC444；每次清理日志并保存原始输出。
4. 按 S0 相同场景执行 before/after A/B；不一致时标记 `UNBOUND`。
5. 执行 lifecycle、soak 和 input matrix。
6. 检查 diff、证据索引和脱敏状态。
7. Reviewer 逐项填写实际值、原始路径和 verdict；任何必选项非 PASS 时整体不是 RELEASE READY。

## 5. 判定规则

- `PASS`：Given/When 已执行，Then 可由独立原始证据直接判定为真。
- `FAIL`：原始证据否定 Then，或行为违反 ADR/Story 不变量。
- `UNKNOWN`：没有足够证据、阈值未冻结或材料无法绑定同一运行。
- `UNSUPPORTED`：设备能力明确不支持；不是失败修复任务，也不是 PASS。
- `NOT READY`：前置门未满足或必选项仍非 PASS。

`gpu-validation-video-playback-16s.mp4` 只证明某次运行可见播放和交互；它不能单独证明 hardware decoder、CPU 改善、fallback 或长稳。
