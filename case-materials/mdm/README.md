# MDM 案例六阶段交付包

> 用途：作为培训第 9–25 页的真实文档素材。先展示文档如何生成、如何判断，再补仓库截图、Session 截图和真机视频。

本案例聚焦 SecurityTool 的“系统账号变化后同步防火墙状态”能力。六份文档不是重新发明项目规格，而是把当前仓库已有的原始需求、UX、PRD、RFC、模块设计、专项方案、代码、测试和 Git 历史整理成一条可讲授的证据链。

## 六阶段与产物

| 阶段 | 核心问题 | 本案例产物 | 上游真实来源 |
|---|---|---|---|
| 1. 资产同步 | 我们到底收到了什么，哪些材料互相冲突 | `01-资产同步与冲突清单.md` | 原始 Excel、AI 修正版、UX 原型、PRD、代码 |
| 2. 方案推导 | 有哪些方案，为什么选这个而不是另一个 | `02-方案推导与决策记录.md` | 当前问题、代码职责、失败模式 |
| 3. RFC | 系统边界、真相源、状态和失败语义是什么 | `03-防火墙账号同步RFC.md` | 总体 RFC、模块设计、专项方案 |
| 4. Story | Feature 如何切成一轮轮可独立验收的任务 | `04-Feature与Story拆解.md` | 代码边界、测试边界、真实提交序列 |
| 5. Ralph 迭代 | 每轮如何拿任务、执行、验证、写回和停止 | `05-Ralph迭代运行账.md` | Git 提交、测试、文档先行记录 |
| 6. 测试验收 | AI 完成后，凭什么给 PASS | `06-测试验收报告.md` | 当前测试结果、E2E 资产、设备门 |

## 课堂统一读法

每份文档都回答五个问题：

1. 输入是什么。
2. AI 做了什么加工。
3. 人需要判断什么。
4. 生成的结构化文档是什么。
5. 下一阶段凭什么可以开始。

## 培训页与实操安排

- 第 9–22 页：按“资产同步 → 方案推导 → RFC → Story → Ralph”推进，共安排 5 个短实操；每次都要求留下结构化产物，而不是只听概念。
- 第 23 页：MCP 介绍整页预留，直接替换为讲师已有材料；本稿只保留“工具成功不等于业务验收成功”的转场结论。
- 第 24–25 页：预留 2 页 E2E。第 24 页使用 Runner–Driver–Backend 架构图完成静态路由练习，第 25 页运行或推演真实用例 `FW-STATUS-001`，读取报告并给出 `PASS / FAIL / UNKNOWN`。
- 设备不可用时不取消实操：改为静态展开 Case JSON、Driver、Assertion 与 Artifact，并把设备相关结论明确标为 `UNKNOWN`。

详细页稿与讲师 Runbook 见 `07-PPT第9-25页内容与备注.md`。其 P9–25 内容已经同步到仓库根目录主稿 `harmonyos-sdd-ralph-workshop.md`；后续内容调整应同时维护两处，主稿可直接作为 PPT 制作输入。

代码级调用链、系统 API、失败分支、UT oracle 与 E2E Runner 路由见 `08-代码级调用链与课堂穿刺.md`。讲师至少应完成一次从 `onAccountAdded()` 到 `netFirewall`、再从 Case JSON 到 `CaseResult` 的现场穿刺；只展示架构图或文件树不足以支撑本案例。

整体叙事、逐页主视觉、页内/备注/现场的信息分层，以及仍需补充的真实证据见 `09-MDM案例整体审阅与落版规则.md`。制作 PPT 时优先遵守该文件的落版约束，避免把代码级细节全部堆到页面正文。

## 事实标记

- `REPO FACT`：当前 SecurityTool 仓库可以直接打开或运行验证。
- `GIT FACT`：当前 Git 历史中的真实提交、文件和时间。
- `RUN FACT`：本轮实际执行得到的结果。
- `TEACHING RECONSTRUCTION`：为了培训把多个真实提交整理成阶段或 Story，不声称历史上使用了同名自动化 Runner。
- **【补充素材】**：等待补充真实截图、设备日志或视频。
