## 2. 判定规则

- `PASS`：需求规定的结果已经由对应层的证据证明。
- `FAIL`：证据证明需求未满足或验证门失败。
- `UNKNOWN`：关键验证未执行或工具/设备不可用；不能按通过处理。

任何低层 PASS 都不能覆盖更高层 FAIL/UNKNOWN：

```text
文档/静态 → UT → 构建 → 签名安装 → 设备操作 → 系统业务事实
```

## 6. E2E 与业务事实的边界

仓库已有防火墙 E2E 资产：

- `FW-MODE-001`：公共/私有模式卡可见。
- `FW-STATUS-001`：认证后的开关流程回到稳定页面。
- `FW-RULE-001`：创建域名规则后列表可见。

这些 case 对界面和操作链有价值，但其 notes 已明确部分 primary assertion 未来仍需系统 getter 支撑。因此：

- 文本可见 ≠ 系统 policy 正确。
- 规则列表出现 ≠ 系统规则已经下发。
- 安装成功 ≠ 企业管理员激活。
- MCP/tool success ≠ 业务 success。

### E2E 代码路由

```text
Case JSON
→ validate_case_contract
→ normalize_case_definition(flow/assertions → execution_steps)
→ E2ERunner.run_case / run_step
→ flow_action: SecurityToolFlowExecutor.execute
→ entity action: resolve_operation_binding + ACTION_TEMPLATES
→ McpDriver/HdcDriver
→ assertion_action: AssertionExecutor.execute
→ CaseResult(status/failure_stage/primary_evidence/secondary_evidence)
→ JSON/Markdown Reporter + artifacts
```

以 `FW-RULE-001` 为例，`entity.create` 被解析为 `firewall.rule.create.domain`，模板再展开为 `open_firewall_rules_page` 和 `submit_firewall_rule_form`。最后的 `assert_text_presence('www.baidu.com')` 只读取 UI 文本事实：Backend 无法判断时为 UNKNOWN、文本不符为 FAIL、文本相符为 PASS。系统规则是否存在仍需 `getNetFirewallRules(userId, ...)` 级别的 readback。
