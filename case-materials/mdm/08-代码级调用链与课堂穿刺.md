> 用途：为第 14、17、19、21、22、24、25 页提供可直接走读的代码事实。路径、类名和函数名均来自当前 `C:/Users/mu/Desktop/code/security_tool`。这份材料不是把代码堆进 PPT，而是保证讲师能从页面结论继续下钻到真实实现、失败语义和测试 oracle。

## 1. 一句话讲清这条 Feature

系统账号新增时，`EnterpriseAdminAbility` 收到的 `accountId` 只是触发信号；系统必须等 `getOsAccountLocalIds()` 返回的完整集合真正包含该 ID，才允许防火墙模块按当前模式对最新集合做业务同步。业务同步成功后保存 `mode + userIdsSignature`，再跨进程通知前台重读展示数据。

完整链路分成两个闭环：

```text
后台业务闭环
EnterpriseAdminAbility.onAccountAdded(123)
→ scheduleAccountReconcile('account-added', 123)
→ AccountChangeCoordinator.schedule(...)
→ loadStableSnapshot(...)
→ SystemUserProvider.loadAvailableUserIds()
→ osAccount.AccountManager.getOsAccountLocalIds()
→ buildSnapshot(signature/added/removed)
→ dispatchHandlers(...)
→ FirewallAccountChangeHandler.handle(...)
→ prune / policy / rules / mode transaction
→ 无前序失败时尝试写入 lastAppliedMode + lastAppliedUserIdsSignature

前台展示闭环
AccountChangeEventBus.publishSnapshot(...)
→ commonEventManager.publish(...)
→ AccountRuntimeService.handleAccountChange(...)
→ ApplicationRuntimeManager.handleAccountChange(...)
→ FirewallOverviewViewModel.refresh(...)
→ FirewallRulesViewModel.refreshForAccountChange(...)
→ 重读 userOptions / policy / rules
```

课堂首先让学员区分：前一个闭环决定“系统状态有没有收敛”，后一个闭环只决定“页面是否显示最新结果”。页面刷新不能代替业务闭环。

## 1.1 核心函数契约总表

| 函数 | 输入 | 输出 | 主要副作用 | 失败/边界 |
|---|---|---|---|---|
| `EnterpriseAdminAbility.onAccountAdded(accountId)` | 系统回调 ID | `void` | keep-alive 注册；提交 reconcile 请求 | 不等待业务结果；异常只记录日志 |
| `AccountChangeCoordinator.schedule(context, source, triggerId)` | Context、事件类型、触发 ID | `void` | 更新 `pendingRequest`；重置 400ms timer | fire-and-forget；调用方拿不到 Handler 结果 |
| `runPending()` | 当前 pending 状态 | `Promise<boolean>` | single-flight；串行处理执行中新增请求 | Handler 任一失败使 allSuccess=false |
| `loadStableSnapshot(request)` | 事件请求 | `{snapshot, stable, attemptCount}` | 最多 6 次读取账号集合 | added ID 始终不可见时 stable=false |
| `SystemUserProvider.loadAvailableUserIds()` | 无 | `UserFirewallListResult` | 调用账号系统 API；构造标签 | API 失败与真实空列表都返回 `users=[]` |
| `buildSnapshot(...)` | 当前/上次集合 | `AccountSnapshotChange` | 无系统副作用 | signature 只是排序 ID 字符串，不是业务成功标记 |
| `dispatchHandlers(context, snapshot)` | 稳定快照 | `Promise<boolean>` | 顺序调用所有 Handler | 单个 Handler 抛错被捕获，继续汇总 false |
| `FirewallAccountChangeHandler.handle(...)` | Context、账号快照 | `Promise<boolean>` | prune；下发 policy/rules；保存 apply state | 空集合保守跳过；三种模式走不同分支 |
| `FirewallModeSwitchService.applyModeToUsers(...)` | 模式、用户、开关目标 | `FirewallOperationResult` | 快照、清理、下发、映射、回滚 | 补偿式回滚；本地 apply state 非原子 |
| `FirewallLocalRepository.saveModeApplyState(...)` | mode、signature | `Promise<boolean>` | 连续写两个 Preference key | 可部分成功；没有事务边界 |
| `AccountChangeEventBus.publishSnapshot(...)` | 稳定账号快照 | `void` | 发布跨进程 common event | 不携带 Handler success/failure |
| `FirewallRulesViewModel.refreshForAccountChange(...)` | Context、用户列表 | `Promise<void>` | 替换 userOptions，重读 policy/rules | 只影响展示；失败清空页面数据并记录错误 |

讲师每次下钻代码都按同一顺序问：输入从哪里来、它决定了什么、写了哪些状态、失败返回给谁、调用方是否真的处理了失败。

## 2. 入口：事件只负责排队，不直接操作防火墙

### 真实代码锚点

文件：`entry/src/main/ets/enterpriseadminability/EnterpriseAdminAbility.ets`

```ts
onAccountAdded(accountId: number): void {
  this.ensureKeepAliveAppRegistered('onAccountAdded', accountId)
  this.scheduleAccountReconcile('account-added', accountId)
}

private scheduleAccountReconcile(source, accountId): void {
  registerDefaultAccountChangeHandlers()
  AccountChangeCoordinator.schedule(this.context, source, accountId)
}
```

这里做了三件事：

1. 回调参数 `accountId` 被保留下来，作为后续稳定条件。
2. `registerDefaultAccountChangeHandlers()` 保证防火墙 Handler 已进入注册表。
3. Ability 不读取账号全集，也不调用 `netFirewall`；它只把请求交给协调器。

### 怎么判断设计是对的

- Ability 中不出现 `setNetFirewallPolicy()`、`addNetFirewallRule()` 等业务副作用。
- 事件 ID 不被直接 append 到账号全集。
- 新模块要响应账号事件时，新增 `AccountChangeHandler` 并注册，不改事件源。

```text

AccountChangeHandler.ets → handle(context, snapshot)
```

## 3. 协调器：400ms 防抖、单飞执行、条件重试

文件：`entry/src/main/ets/services/account/AccountChangeCoordinator.ets`

### 3.1 调度与并发语义

`schedule()` 把最新请求写入 `pendingRequest`，清掉旧 timer，再启动 400ms 定时器。`runPending()` 用 `running` 保证同一时间只有一个 reconcile；执行中如果又有事件到达，新的请求仍写进 `pendingRequest`，当前轮结束后 while 循环继续处理。

```text
schedule
  pendingRequest = latest request
  clear previous timer
  setTimeout(400ms)
      ↓
runPending
  running=true
  while pendingRequest != null
      take request
      pendingRequest=null
      runOnce(request)
  running=false
```

这不是简单 debounce：`timerId` 合并短时间事件，`running + pendingRequest` 解决执行中的连续事件。

### 3.2 稳定快照门

常量：

```ts
ACCOUNT_CHANGE_DEBOUNCE_MS = 400
ACCOUNT_ADDED_STABLE_RETRY_INTERVAL_MS = 200
ACCOUNT_ADDED_STABLE_MAX_RETRIES = 5
```

`loadStableSnapshot()` 的判断不是“等一段时间”，而是“等待业务条件成立”：

```text
第一次 loadSnapshot
→ source != account-added：立即稳定
→ source == account-added 且 currentUserIds 包含 triggerAccountId：稳定
→ 否则每 200ms 重读一次，最多 5 次
→ 仍不包含：stable=false
```

`runOnce()` 在 `stable=false` 时直接返回 `false`，不会执行 Handler，也不会发布前台事件。稳定后才更新 `previousUserIds`、分发 Handler，并发布稳定快照。

### 3.3 快照中到底有什么

`buildSnapshot()` 用标准化后的完整集合计算：

```text
currentUserIds      当前完整集合
previousUserIds     协调器上次稳定集合
addedUserIds        current - previous
removedUserIds      previous - current
signature           排序去重后的 current，以逗号连接
previousSignature   排序去重后的 previous
```

例如 `[122,100,123,123]` 被标准化为 `[100,122,123]`，签名为 `100,122,123`。签名不是安全哈希，而是用于快速判断“相同模式是否已经处理过相同账号集合”。

### 当前实现边界

`SystemUserProvider` 在 API 异常和真实空列表时都会返回 `users=[]` 加空态消息。Handler 对空集合选择“不 prune、不重放”；这是保守失败，但当前模型不能仅凭返回值区分“系统真的没有账号”和“读取失败”。课堂应把它列为可继续演进的可观测性缺口，而不是假装已经完全解决。

## 5. Handler：同一个账号快照为什么要走三条分支

文件：`entry/src/main/ets/services/firewall/FirewallAccountChangeHandler.ets`

### 5.1 共同前置

```text
snapshot.currentUserIds 为空
→ return true；不 prune、不重放

非空
→ FirewallLocalRepository.pruneUnavailableUsers(validUserIds)
→ 失败则 return false
→ 读取 currentMode 与 desiredEnabled
```

`pruneUnavailableUsers()` 同时清理三类本地引用：

1. `ruleIntents[].targetUserIds` 中的失效账号。
2. 对应的 `ruleDeployments`。
3. `FirewallUserPolicyModeRecord` 历史记录。

它不调用被删除账号的系统防火墙 API，避免把“系统已删除账号”再次当成可调用对象。

### 5.2 custom 分支

```text
currentMode == custom
→ FirewallPolicyService.applyPolicyForMode(custom, snapshot.users, desiredEnabled)
→ 逐账号读取现有 policy
→ 根据本地 per-user mode 生成默认 policy
→ FirewallSystemRepository.setPolicy
→ 全部成功后 saveModeApplyState(custom, signature)
```

关键点：该分支没有调用 `FirewallModeSwitchService.applyModeToUsers()`，因此不会重新生成并扩展历史自定义规则。`FirewallModeStrategy.buildCustomRules()` 只从既有 intent 的 `targetUserIds` 生成规则，新账号不会自动进入旧 intent。

### 5.3 public/private 分支

```text
读取 lastAppliedMode + lastAppliedUserIdsSignature
→ mode 和 signature 都相同：幂等跳过
→ 否则 FirewallModeSwitchService.applyModeToUsers(...)
```

这条分支的目标是“预置模式对最新完整集合生效”，所以账号签名变化时必须重放。

### 5.4 成功与失败怎么向上传递

- `custom`：policy 失败或 `saveModeApplyState` 返回 false 时，Handler 返回 `false`。
- `public/private`：`applyModeToUsers().success=false` 返回 `false`。
- Coordinator 会把 Handler 失败汇总到 `allSuccess=false`，但稳定账号事实仍会通过 EventBus 发布，前台可刷新展示；“业务下发失败”和“账号事实稳定”是两个不同结论。
- 当前 `schedule()` 是 fire-and-forget，Handler 失败不会在 Coordinator 内自动重试，EventBus payload 也不携带 Handler 结果。因此业务失败必须靠日志、验收 Runner 或后续显式 reconcile 暴露，不能靠前台刷新判断。

## 6. 模式事务：先快照，再清理/下发，失败时尝试回滚

文件：`entry/src/main/ets/services/firewall/FirewallModeSwitchService.ets`

`applyModeToUsers()` 的真实顺序：

```text
1 createSnapshot(users)
  ├─ getPolicy(userId)
  ├─ listRules(userId)
  ├─ getCurrentMode()
  └─ loadRuleIntentMappingData()

2 clearRules(userId) for each user
3 applyPolicyForMode(targetMode, users, desiredEnabled)
4 clearAllRuleDeployments()
5 FirewallModeStrategy.buildRulesForMode(targetMode, users)
6 FirewallSystemRepository.addRule(rule)
7 replaceRuleDeployments(localRuleId, deployments)
8 进入本地提交块前无 failedItems 时，调用 saveCurrentMode(targetMode)
9 随后仍会调用 saveModeApplyState(targetMode, signature)
10 任一步失败 → rollbackToSnapshot(...)
```

对应系统 API：

```text
getPolicy       → netFirewall.getNetFirewallPolicy(userId)
setPolicy       → netFirewall.setNetFirewallPolicy(userId, policy)
listRules       → netFirewall.getNetFirewallRules(userId, requestParam)
addRule         → netFirewall.addNetFirewallRule(rule)
removeRule      → netFirewall.removeNetFirewallRule(userId, systemRuleId)
```

### 为什么先保存系统快照

模式切换会清规则、改 policy、重新生成规则并改本地映射，任何一步失败都可能形成部分提交。`createSnapshot()` 保存原模式、原 intent/deployment、每个用户的 policy 和系统规则；`rollbackToSnapshot()` 尝试恢复。

### 设计上为什么签名必须最后、原子地写

`lastAppliedUserIdsSignature` 是幂等门。如果系统规则只下发一半就提前写新签名，下次事件会因为“模式和签名没变”而跳过，失败状态被永久伪装成已处理。正确契约应是：系统操作和本地映射无失败后，再把 current mode、last applied mode、signature 作为一个提交单元写入；任一失败都要恢复旧值或明确标记脏状态。

### 回滚边界必须如实说明

回滚本身也可能失败，失败项会继续进入 `failedItems`。所以这里提供的是“补偿式回滚尝试”，不是数据库意义上的强事务。课堂验收不能只看函数返回 `false`，还要保留原始失败项和回滚失败项。

### 代码审阅发现的真实缺口

1. `saveCurrentMode()` 失败后，当前代码仍继续调用 `saveModeApplyState()`；可能出现 overall=false，但新 `lastAppliedMode/signature` 已写入。
2. `saveModeApplyState()` 内部连续写两个 Preference key，返回 `modeSaved && signatureSaved`，不是原子事务；其中一个写入成功、另一个失败时会产生部分状态。
3. `rollbackToSnapshot()` 恢复系统 policy/rules、本地 mapping 和 `currentMode`，但没有恢复 `lastAppliedMode/lastAppliedUserIdsSignature`。
4. `FirewallSystemRepository.listRules()` 读取异常时回退为 `[]`，`createSnapshot()` 无法区分“真实无规则”和“规则读取失败”，存在用不完整快照继续破坏性切换的风险。

因此，当前实现能证明核心稳定快照协议和主分支逻辑，但“本地状态原子提交”和“完整回滚”仍应标记为待补 Story，而不是宣称事务已经完备。

## 7. 前台消费：页面为什么不直接订阅系统账号事件

### 发布端

文件：`entry/src/main/ets/services/account/AccountChangeEventBus.ets`

`publishSnapshot()` 只发布 `account-added/account-removed` 的稳定快照，payload 包含：

```text
source
triggerAccountId
signature
timestamp
```

它使用 `commonEventManager.publish()` 跨进程传递结果，不把完整账号对象塞进事件。

### 消费端

```text
AccountRuntimeService.start()
→ AccountChangeEventBus.subscribe(listener)
→ handleAccountChange(payload)
→ ApplicationRuntimeManager.handleAccountChange(payload)
→ Promise.all(
     refreshPermissionForAccountChange,
     refreshFirewallOverviewForAccountChange,
     refreshFirewallRulesForAccountChange
   )
```

防火墙规则页分支再次调用 `SystemUserProvider.loadAvailableUserIds()`，然后：

```text
FirewallRulesViewModel.refreshForAccountChange(context, users)
→ userOptions = users
→ reloadDefaultPolicies(context)
→ reloadRules(context, users)
→ dataLoaded = true
```

这一步是展示模型收敛，不是业务下发。它只在 ViewModel 已加载、页面运行时存在时执行；后台业务正确性不依赖页面是否打开。

## 9. E2E：从 Case JSON 到 MCP/HDC 和报告的真实代码链

以 `scripts/e2e/cases/firewall/rule_create.json` 为例：

```text
Case JSON
  flow: app.launch / navigation.open_page / entity.create / ui.capture_screenshot
  assertion: assert_text_presence('www.baidu.com')
        ↓
E2ERunner.run_case()
  validate_case_contract(raw_case)
  normalize_case_definition(raw_case)
        ↓
execution_steps
  flow → type=flow_action
  assertion → type=assertion_action
        ↓
E2ERunner.run_step()
  flow_action → SecurityToolFlowExecutor.execute(ref, params)
  assertion_action → AssertionExecutor.execute(type, value, params)
```

### `entity.create` 如何变成真实 UI 操作

```text
entity.create(domain=firewall, entity=rule, variant=domain)
→ resolve_operation_binding()
→ template_key = firewall.rule.create.domain
→ bridge_action = execute_template_action
→ ACTION_TEMPLATES[template_key]
   1 open_firewall_rules_page(rule_type=domain)
   2 submit_firewall_rule_form(domain/direction/policy/...)
→ McpDriver.execute(MpcActionRequest)
→ HarmonyOS MCP Bridge / Backend / UI tools
```

### Assertion 怎样决定 PASS/FAIL/UNKNOWN

`assert_text_presence` 进入 `AssertionExecutor.execute()`：

```text
McpDriver.text_presence(...)
→ backend 无法给出可判定事实：UNKNOWN
→ exists != expected_present：FAIL
→ exists == expected_present：PASS
```

`E2ERunner.run_case()` 再应用 `result_policy`：

- 任何 step `FAIL`：记录 `failure_stage` 和 primary evidence；默认停止。
- `UNKNOWN`：case 状态为 UNKNOWN；若 `allow_unknown=false` 再升级为 FAIL。
- 每步 evidence 进入 `secondary_evidence`。
- 最后 `validate_result_contract(case_result)`，Reporter 再写 JSON/Markdown 和 artifacts。

### 当前证据边界

`FW-RULE-001` 当前主断言是列表文本出现，只证明 UI 可见。Case notes 已明确未来需要防火墙 getter。要证明系统规则真的存在，还需补：

```text
Firewall getter/readback
→ userId + rule type + domain + direction + action
→ 与 Case 输入逐字段比较
→ 结果进入 primary evidence
```

因此课堂判定应写“UI E2E PASS，系统规则事实 UNKNOWN”，而不是笼统写“防火墙规则创建 PASS”。

### 9.1 E2E 核心函数契约

| 函数 | 输入 | 输出/状态 | 关键责任 |
|---|---|---|---|
| `validate_case_contract(raw_case)` | 原始 JSON | 成功或 ContractError | 拒绝旧 `steps` 格式和非法字段 |
| `normalize_case_definition(case)` | flow + assertions | `execution_steps` | 将业务动作和断言统一成 Runner 步骤，但仍保留类型差异 |
| `E2ERunner.run_case(case_path)` | Case 文件 | `CaseResult` | 顺序执行、应用 stop/unknown policy、汇总 evidence |
| `E2ERunner.run_step(step)` | 一个标准步骤 | `StepResult` | 按 `flow_action/assertion_action/hdc/...` 分派 |
| `resolve_operation_binding(ref, params)` | `entity.create` 等抽象动作 | template key + bridge action | 把领域动作绑定到产品模板 |
| `SecurityToolFlowExecutor.execute(ref, params)` | flow ref | `FlowExecutionResult` | 选择 HDC/MCP，执行模板或专用 flow |
| `McpDriver.execute(request)` | action/params/expected | `McpExecutionResult` | 经过 Bridge/Backend 调用 UI 工具 |
| `AssertionExecutor.execute(...)` | assertion type/value/params | PASS/FAIL/UNKNOWN | 独立判断事实，不接受 Driver success 代替断言 |
| `validate_result_contract(case_result)` | 完整结果 | 成功或 ContractError | 保证报告字段和状态结构有效 |

最容易误讲的地方是 `normalize_case_definition()`：它把 flow 和 assertion 放进一个执行序列，并不代表二者语义相同。前者改变/操作环境，后者判断结果；报告必须保留这个区别。

## 12. 讲师必须明确的四个“不等于”

```text
onAccountAdded 已触发       ≠ 新账号已出现在完整集合
ViewModel 已刷新            ≠ 防火墙系统 policy 已正确下发
MCP action 返回 PASS        ≠ 业务 assertion 已通过
816 个 UT PASS              ≠ 真机账号时序和系统规则已验收
```

这四个“不等于”就是本案例从代码实现过渡到工程验收的主线。
