# MDM 外设管理｜代码级调用链与课堂穿刺

## 1. 一句话讲清源码主线

用户在 `PeripheralPage` 操作受控组件，父级 `PeripheralViewModel` 做管理员门禁和跨 Tab 协调，子 ViewModel 管理可见状态，领域 Service 编排系统副作用，Repository 保存默认意图和设备状态，最终通过 MDM 回读与真实 USB 行为验收。

全链统一优先级：接口管控全局闸门 > fingerprint 单设备显式规则 > 未配置设备默认黑/白名单；USB 存储模式作为并行类型策略覆盖存储设备最终可用性。

## 3. 页面到父 ViewModel

### 3.1 USB 全局开关

```text
InterfaceControlTab.onUsbInterfaceToggleAsync
  → PeripheralPage.handleUsbInterfaceToggle(disallow)
  → PeripheralViewModel.toggleInterface('usb', disallow)
  → ensureAdminReady()
  → InterfaceControlViewModel.toggleInterface('usb', disallow)
```

父 VM 只做三件事：权限门、reasonCode、成功后的 Policy VM 刷新。

```ts
this.reasonCode = await this.interfaceControl.toggleInterface(feature, disallow)
if (this.reasonCode === null && feature === 'usb') {
  await this.policy.reloadRecords()
}
return this.reasonCode === null
```

判断是否越层：如果这里出现 `addDisallowedUsbDevices()`、Preferences 或 RDB SQL，MVVM 边界就被破坏。

### 3.2 默认策略

```text
PolicyList.onDefaultPolicyChange
  → PeripheralPage
  → PeripheralViewModel.setUsbDefaultPolicy(index)
  → PeripheralPolicyViewModel.setUsbDefaultPolicy(index)
  → PeripheralDevicePolicyRepository.setUsbDefaultPolicy(policy)
```

全链路没有枚举设备、没有 MDM 下发，这正是“默认值只影响未来新设备”的代码证据。

### 3.3 单设备动态规则

```text
PolicyList.onPolicyChange
  → PeripheralViewModel.handlePeripheralPolicyChange(...)
  → policy.startUpdate(deviceId)
  → PeripheralPolicyViewModel.setDevicePolicy(...)
  → UsbDevicePolicyStateService.setPolicy(fingerprint, policy)
  → PeripheralDevicePolicyDispatchService.dispatch(...)
  → 成功后 Repository.upsert(nextState)
  → 写 policy_snapshot
  → reload records + policy
  → policy.endUpdate(deviceId)
```

## 4. 全局 USB 代码穿刺

入口分支：

```ts
if (feature === PeripheralInterfaceFeatures.USB) {
  const result = await UsbGlobalPolicyService.setDisabled(disallow)
  if (!result.success) return normalizeReason(...)
  this.updateInterfaceState(feature, disallow)
  return null
}
```

这段代码证明 ViewModel 是“成功后提交”。真正的事务在 Service：

```text
disable=true
  → read storage policy
  → require READ_WRITE
  → suspendActivePolicies
  → captureCurrentUsbDevices
  → set global restriction
  → failure: restorePresentDeniedPolicies
  → success: append deny snapshot

disable=false
  → set global restriction false
  → restorePresentDeniedPolicies
  → wait 500ms / empty then 1000ms
  → capture devices
  → append allow snapshot
```

课堂让学员找三个不同失败等级：

1. 存储冲突：主操作未开始，直接失败。
2. suspend 失败：补偿已暂停项，主操作不开始。
3. trace snapshot 失败：主策略已成功，不回滚，只告警。

## 5. 默认策略代码穿刺

仓储默认：

```ts
private static usbDefaultPolicy: PeripheralDevicePolicy = 'allow'
const value = await pref.getString('usb_default_policy', 'allow')
return policy === 'deny' ? 'deny' : 'allow'
```

三个安全含义：

- 新安装默认不误封；
- 旧数据损坏不误封；
- 初始化失败回到 allow。

动态设置：

```ts
const saved = await saveUsbDefaultPolicy(normalized)
if (!saved) return false
usbDefaultPolicy = normalized
notifyChanged()
```

只在持久化成功后更新内存并通知 listener，避免刷新成未保存状态。

## 6. 首次连接代码穿刺

核心代码：

```ts
const existing = await stateRepo.get(identity.fingerprintKey)
const desired = existing?.desiredPolicy ??
  (defaultRepo.isUsbDefaultDeny() ? 'deny' : 'allow')

if (desired === 'deny' && !skipDeviceDenyDispatch) {
  dispatchResult = await dispatch(...)
  if (dispatchResult.success) nextState.activePolicy = 'deny'
} else if (desired === 'allow') {
  nextState.activePolicy = 'none'
}

const shouldSave = desired === 'allow' ||
  existing !== null ||
  dispatchResult?.success === true
```

让学员推演四行测试：

| existing | default | dispatch | 是否保存/状态 |
|---|---|---|---|
| 无 | allow | 不调用 | 保存 allow/none |
| 无 | deny | 成功 | 保存 deny/deny |
| 无 | deny | 失败 | 不建假黑名单 |
| 有 allow/deny | 任意 | 按已有意图 | 默认值被忽略 |

## 7. 拔出与系统粒度

代码检查 `hasOtherActiveDeny(baseClass, fingerprint)`，是因为系统下发使用 `UsbDeviceType.baseClass`，而不是 fingerprint。

```text
当前设备 active=deny
  ├─ 同类型还有在线 active deny：不 remove 系统类型策略，只把当前 active=none
  └─ 没有：dispatch allow 清理类型策略；成功后 active=none
```

课堂追问：既然系统按类型，页面为什么仍显示“单设备”？答案是 fingerprint 管理业务意图和资产身份，系统执行受平台粒度限制。验收必须加入“同 baseClass 第二设备”。

## 8. 还原策略代码穿刺

系统清理：

```ts
const disallowed = usbManager.getDisallowedUsbDevices(ADMIN_WANT)
if (disallowed.length > 0) {
  usbManager.removeDisallowedUsbDevices(ADMIN_WANT, disallowed)
}
```

本地恢复：

```ts
if (!clearResult.success) return false
for (const record of records) {
  restored.push(copyStateWithPolicy(record, 'allow', 'none'))
}
return await repo.upsertAll(restored)
```

这个顺序提供一个直接的审阅规则：任何“先把 UI/数据库改成 allow，再尝试清系统策略”的补丁都应拒绝。

## 9. USB 存储冲突与双层防线

UI/VM 层：

- Policy VM 在 storage DISABLED 时把 USB_STORAGE record 的 `editable` 设为 false。
- 全局 USB 禁用时默认策略、名单行和还原按钮都置灰。

Domain/Adapter 层：

```ts
if (deviceType === USB_STORAGE && storagePolicy === DISABLED) {
  return usb_conflict_account_storage
}
```

两层都需要：UI 置灰用于可用性，后端校验用于不变量和防绕过。

## 10. 动态刷新链

```text
Preferences default policy changed
  → PeripheralDevicePolicyRepository listener
  → PeripheralViewModel.refreshPolicyDrivenData()
  → PeripheralPolicyViewModel.reloadRecords()

USB policy state changed
  → UsbDevicePolicyStateRepository listener
  → 同上

Trace changed
  → PeripheralTraceEntryRepository listener
  → refreshTraceDrivenData()
  → 只刷新连接记录
```

这种事件分流避免“清空 trace 顺便重建/删除名单”的耦合。

### 10.1 Trace 写入链的真实风险

```text
USB event
  → Consumer 生成 PeripheralTraceRecord
  → PeripheralTraceMaintenanceService.appendEntries()
  → upsertBatch() 写入成功
  → deleteExpired()
  → trimToMaxEntries()
  → notifyChanged()
  → PeripheralViewModel.refreshTraceDrivenData()
```

当前 `notifyChanged()` 位于维护步骤之后。真实 Session 曾出现 RDB 已有 connect 记录，但没有 `refreshTraceDrivenData`，切 Tab 后才显示。审阅时应检查：若清理或裁剪失败，是否会吞掉“写入已成功”的发布通知。

建议的契约顺序是：

```text
写入事务成功
  → 立即发布事实
  → 再做保留期/上限维护
  → 维护失败单独告警
```

这不是简单加刷新，而是区分主提交和维护副作用。

### 10.2 `present` 在线态链的真实风险

```text
ATTACHED  → handleConnect → present=true
DETACHED  → handleDisconnect → present=false
```

如果应用未运行时拔出，或 detach 的 SN/description 与 attach 不一致，旧 fingerprint 可能保持 `present=true`。页面再次打开只读 RDB 仍无法自愈。完整框架应在运行时启动/恢复时枚举 `usbManager.getDevices()`，对 RDB 做在线集合对账：规则保留、离线态修正、动态操作禁用。

## 11. UI 状态不等于系统状态

代码审阅时把变量分成三栏：

| 类型 | 示例 | 可信范围 |
|---|---|---|
| UI 工作态 | `processingKey/updatingKeys` | 只说明正在操作 |
| 应用业务态 | `desiredPolicy/present/activePolicy/defaultPolicy` | 说明本地意图/执行记录 |
| 系统真源 | restrictions/USB storage/disallowed types | 说明 MDM 当前策略 |

真正验收再加第四栏：实物设备是否可用。四栏不一致时，不允许用其中一栏覆盖其它事实。

### 11.1 错误码调用链也要追到底

```text
Policy UI / Interface UI
  → ViewModel reasonCode
  → Dispatch / PeripheralService
  → MDM error code
  → system getter
  → hilog Mount/Unmount/authorized
  → physical behavior
```

- `9200010`：优先查系统残留类型规则和策略冲突，不先归因管理员权限。
- `9200007`：若 getter 已到目标，继续查重新挂载/重枚举；它可能是部分生效。

reasonCode 是给用户的行动建议，不是根因真源。根因要由最底层仍与预期分叉的证据决定。

## 14. 讲师必须强调的八个“不等于”

1. UI 禁用不等于系统已禁用。
2. `desiredPolicy=deny` 不等于 `activePolicy=deny`。
3. fingerprint 单设备身份不等于系统下发是单设备粒度。
4. E2E PASS 不等于 MDM 与实物 PASS。
5. 覆盖率高不等于需求完整；覆盖率低也不能靠口头补齐。
6. 接口管控启用不等于所有单设备 deny 被删除。
7. API 返回失败不等于系统完全没有提交。
8. RDB 已写入不等于 ViewModel 已收到变更通知。
