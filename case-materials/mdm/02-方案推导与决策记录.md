# 阶段 2｜方案推导与决策记录

## 1. 从需求进入一个真实 Feature

Feature：系统账号新增或删除后，防火墙的系统 policy、系统规则和本地记录与最新账号集合保持一致。

真实需求来自 `docs/superpowers/plans/2026-07-02-firewall-account-reconcile.md`：

- public/private：新增账号补下发当前模式 policy 和预置规则。
- 删除账号：清理本地 rule intent 作用域、deployments 和用户历史记录。
- custom：同步账号级默认 policy，但不自动扩大旧规则作用域。
- UI 只展示业务 reconcile 的结果，不用强制刷新掩盖底层错误。

## 2. 先画问题链，不先画类图

```text
系统账号变化
→ EnterpriseAdminAbility 收到事件
→ 如何获得“最新完整账号集合”
→ 谁决定 added / removed
→ 哪些模块需要响应
→ 防火墙如何重放/清理
→ UI 如何获得稳定事实
→ 如何证明系统策略真的正确
```

这一阶段 AI 要输出“未知项 + 备选方案 + 取舍”，不能只给一个看似完整的架构图。

## 3. 方案对比

| 方案 | 做法 | 看起来的优点 | 真实风险 | 决策 |
|---|---|---|---|---|
| A. Provider 直接同步防火墙 | `SystemUserProvider` 读取账号后直接做策略副作用 | 代码少 | 真相源与业务副作用耦合；权限管理无法复用 | 拒绝 |
| B. 只信事件 ID | `onAccountAdded(123)` 直接把 123 加入目标集合 | 快 | 不能代表完整集合；删除/并发/重命名语义不完整 | 拒绝 |
| C. 页面重进强制刷新 | 在 `MainPage` 或规则页 onShow 重新加载 | 演示容易“看起来正常” | 后台 policy 和本地数据仍可能错误 | 拒绝 |
| D. 协调器 + 全量快照 + Handler | 事件只触发；Provider 读完整集合；协调器分发稳定快照 | 真相源单一、可扩展、可测试 | 需要状态、并发和失败语义 | 选择 |

## 4. 选定方案的逻辑

### 真相源

- 事件：只证明“可能发生变化”。
- `SystemUserProvider.loadAvailableUserIds()`：提供完整账号集合。
- 本地 `lastAppliedUserIdsSignature`：证明上一次成功处理到了哪个集合。

### 所有权

- `EnterpriseAdminAbility`：接事件，不写防火墙策略。
- `AccountChangeCoordinator`：防抖、串行、读快照、计算差量、分发。
- `FirewallAccountChangeHandler`：执行防火墙模块的 prune、重放或默认 policy 同步。
- `FirewallRulesViewModel`：消费稳定结果，刷新页面模型。

### 失败语义

- 账号读取失败/空列表：不 prune、不重放。
- 模式下发失败：不保存新签名。
- custom 模式：不把新增账号解释为历史规则的动态 ALL。
- 连续事件：防抖并串行，执行中收到新事件则在本轮后基于最新集合再跑。

## 5. 技术穿刺如何改变方案

真实复现：`onAccountAdded(123)` 已到达，但首次读取仍为旧集合 `100,112,122`。

这条证据否定了“事件后读取一次就够”的隐含假设。方案因此新增稳定快照门：

```text
account-added + triggerAccountId
→ 读取完整集合
→ 不包含 triggerAccountId：200ms 后重试，最多 5 次
→ 包含：允许分发
→ 超时：FAIL/INCOMPLETE，不更新 previous，不把旧快照当成功
```

当前代码常量：400ms 防抖、200ms 重试、最多 5 次。可迁移思想是“等待业务条件 + 有上限 + 保持旧真相”，不是这些固定数字。
