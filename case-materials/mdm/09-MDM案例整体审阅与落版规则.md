# MDM 外设管理案例｜整体审阅与落版规则

## 1. 整体评价

这版案例已经符合“复杂需求方法论”的主线：不是展示 AI 一次生成代码，而是展示如何从冲突资产中建立真源，推导分层策略，定义真实 MVVM 边界，把 Feature 拆成可验收 Story，再通过多轮失败和证据闭环收敛。

最有教学价值的不是最终开关，而是八个真实矛盾：

- 全局开关与默认策略曾被混为一谈；
- 本地单设备身份与系统类型级下发粒度不一致；
- `desiredPolicy` 与 `activePolicy` 必须分离；
- 还原不能只改本地，必须清系统残留。
- `9200010` 证明本地 allow 不等于系统没有类型 deny；
- `9200007` 证明 API 报错不等于策略完全未提交；
- Trace 已入库不等于变更通知一定发出；
- `present` 事件状态不等于设备永远真实在线。

## 4. 页内、备注、现场三层分工

### 页内

- 一个核心问题；
- 一张结构图、矩阵或证据；
- 1–3 个真实代码锚点；
- 明确结论或 `PENDING`。

### 讲师备注

- 怎么做；
- 怎么判断；
- 不对怎么办；
- 这页证据的边界。

### 现场操作

- 用 `rg` 从页面追到核心 Service；
- 打开一条 UT 解释失败分支；
- 打开 E2E JSON 读 PASS/FAIL/UNKNOWN；
- 若设备可用，展示系统回读和实物插拔。

## 6. 必须留空的素材

没有现成证据时，以下位置保留占位，不生成假截图或假日志：

- USB 全局禁用前后系统回读；
- 默认 allow 新设备进入白名单的视频；
- 默认 deny 新设备被拒绝且进入黑名单的视频；
- 全局恢复后在线 deny 重放的视频/日志；
- 两台同 baseClass 设备的影响面验证；
- 还原前后 EDM 残留对照。
- `9200007` 部分生效后的重插结果；
- 应用未运行时拔出、重新启动后的 `present` 对账；
- Trace 写入成功但维护失败时当前 Tab 仍即时刷新的证据。

## 7. 落版禁区

1. 不再混入旧 MDM 业务案例的文字或素材。
2. 不把所有规则塞到一张抽象流程图。
3. 不把 ViewModel 画成直接调用 RDB/MDM 的“大管家”。
4. 不写“单设备精确阻断”而隐去 baseClass 粒度。
5. 不把 PASS E2E 当成系统业务验收。
6. 不删除旧 FAIL；用后续 PASS 说明问题已收敛。
7. 不把 `PENDING` 用绿色呈现。
